# rtw8822b: Realtek RTL8822BU

Directory: `src/drivers/rtw8822b/` · `0bda:b812` · USB Wi-Fi 5, 2x2

A port of Linux rtw88's RTL8822B support. The register tables
(`rtw8822b_table.c`) are imported from rtw88 with `tools/rtw88_import.py`.

| Part | Where |
|---|---|
| power on, firmware, efuse, MAC, baseband, radio | this directory |
| scanning, joining, block ack, data path | the SoftMAC station, `src/wireless/softmac/` |
| which network to join and when | the Wi-Fi mode ([xedrivers.md](../xedrivers.md#wi-fi)) |

## How it works

Bring-up follows rtw88's probe, power_on and core_start:

1. the MAC is powered;
2. the firmware is downloaded and started;
3. the efuse is read for the card's address;
4. the MAC, baseband and radio are set up;
5. a station port is set on that address and receive starts.

The firmware is `firmware\rtw88\rtw8822b_fw.bin` beside the plugin, the same path
as in linux-firmware. It stays in memory for a later bring-up.

What sets the throughput:

| Setting | Why |
|---|---|
| transmit power from the efuse and the by-rate tables, no regulatory limits; the firmware runs IQK | the AP hears the console at VHT-MCS 9 2SS |
| firmware rate adaptation, block ack both ways, receive aggregation | full rates both ways; the aggregation timeout (0x10) sets how often the host controller stops asking for receive transfers |
| SM power save static off in the HT capability | the AP sends on two streams, not one |
| up to 16 frames in one USB transfer, from the first frame out | one stream out 157 to 169 Mbit/s (19.6 to 21.1 MB/s) |
| at most 16 transmit transfers in flight | same speed as 32, and the host controller stops asking for receive transfers half as often (21 times against 44); 8 is 5% slower |
| the SoftMAC reorder window never moves back and never drops frames it gave up on | dropped frames filled xnet's pool and stopped every connection |

Recovery:

- When the host controller stops asking for receive transfers under heavy sending,
  they are taken back and queued again after about 130 ms. The card is not reset.
- After 4 receive errors in a row the ring is parked, and a receive watchdog resets
  the device. Before, resubmitting at once looped on the USB processor and hung the
  console.
- A transmit watchdog does the same for a stuck transmit.
- Every transmit completion calls `net_tx_done()`. Without it xnet's queue stalls
  under load, which looks like a console hang.

## Issues

- **Out of the console it stops at 159 to 168 Mbit/s (19.9 to 21.0 MB/s), at any
  number of streams.** That is the console's USB host controller sending. The
  profiler shows the copy at 11% of a thread, about 1239 transfers a second of
  about 12 frames, 3.7 in flight. The RTL8156B stops at the same place. Nothing to
  fix in the driver.
- **2.4 GHz sends slowly.** Out is a third of in, because the AP hears the console
  at MCS 10. Lowering the transmit power index (0x30, 0x28, 0x20) made it worse, so
  it is not over-driving. The channel is 14% busy with the console idle. Open.
- **The channel matters.** Channel 100 turned 28% busy with the console idle and
  cost 20 to 30%; hence channel 116.
